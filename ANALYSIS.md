# Анализ проекта AresWare (internal-чит для CS: Source v34)

Статический анализ кода (Windows/MSVC-сборку в этой среде выполнить нельзя, поэтому все
выводы — из чтения исходников). Ссылки даны в формате `файл:строка`.

---

## 1. Краткое резюме

Проект — зрелый по функциональности, но «перегруженный» internal-чит: 7 вкладок меню,
ragebot/legitbot, резолвер, анти-аим, lag-компенсация, ESP/chams, триггербот, конфиги
на оружие. Архитектура в целом правильная (интерфейсы движка → хуки → фичи → UI),
но есть **несколько багов, которые прямо ведут к падению игры**, и заметный
технический долг: 3.5-тысячестрочный `Hooked.cpp`, дублирующиеся конфиг-структуры,
скопированный шесть раз код обработки клавиш, ~1.2 ГБ вендорных исходников в git.

| Метрика | Значение |
|---|---|
| Свои исходники (без ImGui/stb/ассетов) | **22 125 строк**, 60 файлов |
| Самые крупные свои файлы | `Hooked.cpp` 3580, `Valve.hpp` 2249, `Menu.cpp` 2093, `Config.cpp` 1395, `Aimbot.cpp` 1143, `Resolver.cpp` 1012 |
| Вендорное/данные | `Sounds.cpp` 27 730 строк (MP3-массивы), `ImGui.cpp` 10 250 (1.49), `picture.hpp` 4342 (PNG), `MenuIcons.hpp` 625 |
| Всё в репозитории | 84 938 строк в папке проекта, 19 081 файл в git, `.git` = **246 МБ** |

| Конфигурации | `Debug`/`Home` → `v34.dll`, `Release` → `release.dll` |

## 2. Архитектура

### 2.1 Карта слоёв

```
Main.cpp            DllMain → Startup → CheatThread (жизненный цикл, Eject)

  ├─ Hooked.cpp/.hpp      реализации хуков + фичи «в лоб» (анти-аим, strafe, lag и т.д.)
  ├─ Memory.hpp/.cpp      PatternScan, VCall, Safe* helpers
  │    ├─ VmtSwap.hpp/.cpp     подмена vtable (копия + backup)
  │    └─ Detour.hpp/.cpp      код-патч (E9 + NOP)

  ├─ ImGui.*/.DX9/Draw    встроенный Dear ImGui 1.49 + бэкенд D3D9
```

## 3. Что сделано хорошо

1. **Разделение слоёв и абстракции хуков.** `VmtSwap` с backup-vtable + `Detour` с
   backup-кодом, `ScopedMemProtect` (RAII над `VirtualProtect`) — аккуратно.
2. **Обфускация строк** `XorStr` (`Crypt.hpp:117`) — компайл-тайм XOR, ~1400 использований.
   Для internal-чита это базовый must-have, и он есть.
3. **Отсутствие внешних зависимостей**, кроме `d3dx9.lib`: всё вкомпилировано
   (звуки хитмаркера, PNG-иконки меню, шрифты) — DLL самодостаточна.
4. **Динамический резолв API** (`ModuleD`/`GetProcedure`, `Valve.cpp`) вместо IAT — скрывает
   импорты от статического анализа.
5. **Правильные примитивы синхронизации между потоками** — `std::atomic` в `Shared.hpp`,
   команды Load/Save через флаги, а не через прямой вызов из WndProc.
6. **Документирование сложных мест.** `Aimbot.hpp` — образец: каждый приватный метод
   подписан комментарием по-русски. `Resolver.cpp`, `LagCompensation.hpp`,
   `Accuracy.cpp:31-39` — тоже с объяснением «почему именно так».
7. **Защита от NaN/Inf** (`Hooked.cpp:227 IsBadFloat` + `AntiSMAC`) — сетевые проверки
   на бреде в углах сервер ловит, это правильно.
8. **Валидация конфига** — `Clamp()` у каждой структуры, `LimitValue` на загрузке.
9. **Обработка исключений вокруг хуков** (`__try/__except` в `CreateMove`,
   `FrameStageNotify`, `PresentProxy`) — в internal-чите это обязательный минимум.
10. **Лицензия по умолчанию выключена** и корректно реализована: при провале проверки
    `DllMain` возвращает `FALSE`, загрузчик сам выгружает DLL, игра не трогается.

## 4. P0 — баги, которые ведут к падению/некорректной работе

### 4.1 `Memory::SafeDelete/SafeReset/SafeRelease` — молча не работают

`Memory.hpp:40`, `:58`, `:67` — параметр принимается **по значению**:

```cpp
template< typename T >
inline void SafeDelete( T object )   // <-- копия указателя
{
    if( object ) delete object;
    object = nullptr;   // обнуляется локальная копия
}
```

Следствие: в `Config::Release()` (`Config.cpp:70-96`) и `Source::Free()`
(`Source.cpp:449+`) **ни один объект реально не удаляется**, указатели в
`Config::Main/ESP/...` остаются валидными (dangling-подобное состояние: память жива,
но считалась освобождённой логикой). В `VmtSwap`/`Detour` (`make_unique`, `shared_ptr`)
это не проблема, а вот `new`-структуры конфига утекают и второй вызов `Release()`
(теоретически возможный при двойном Eject) будет двойным `delete`.

Лечение — по ссылке:

```cpp
template< typename T > inline void SafeDelete( T& object )  { if( object ) { delete object;    object = nullptr; } }
template< typename T > inline void SafeDeleteArray( T& o )  { if( o )      { delete[] o;        o = nullptr; } }
template< typename T > inline void SafeReset( T& o )        { if( o )      { o.reset();         o = nullptr; } }
template< typename T > inline void SafeRelease( T& o )      { if( o )      { o->Release();      o = nullptr; } }
```

Дополнительно: `Config::Release()` разыменовывает `Main`/`Current` без проверки на
`nullptr` — при частично провалившемся `Startup()` это краш. Добавьте `if( !Main ) return;`
и обнуляйте `Weapon[i] = nullptr;` (сейчас массив остаётся с висящими указателями).

### 4.2 `VmtSwap::Release()` → `Restore()` без проверки, что `Apply()` вообще прошёл

`VmtSwap.cpp:39-53`: `Release()` безусловно вызывает `Restore()`, а тот пишет
`*m_ppInstance = m_pBackupVmt;`, где `m_ppInstance == nullptr`, если `Apply()` не
вызывался или упал на первой проверке (`VmtSwap.cpp:22`: `if( !pInstance )` — а
`Apply` может упасть и на `m_pCustomVmt`).

Сценарий краша (реальный, не теоретический): `Source::Startup()` устанавливает часть
хуков, затем что-то не находит (сигнатура/cvar/шрифт) → `return false` → `Main.cpp:69`
`Eject()` → `Source::Release()` → `m_pClientSwap->Release()`. Если к этому моменту
`Apply()` у какого-то свапа не прошёл — гарантированный Access Violation **в момент
выгрузки**, то есть чит «роняет игру при неудачной инжекции».

Минимальный фикс: в `Restore()` — `if( !m_ppInstance || !m_pBackupVmt ) return;`,
в `Hook()` — `if( nIndex >= m_nSize ) return;` (сейчас `VmtSwap.cpp:56-59` пишет
в массив без проверки индекса — одна опечатка в индексе = перезапись чужой памяти).

### 4.3 `Debug::Print` пишет за границы буфера

`Debug.cpp:15-20`:

```cpp
int i = vsprintf_s( format, sizeof( format ), fmt, args );
format[ i + 0 ] = '\r';
format[ i + 1 ] = '\n';
format[ i + 2 ] = '\0';   // при i >= 2046 — выход за пределы
```

Две проблемы разом:

* при нехватке места в буфере `vsprintf_s` вызывает *invalid parameter handler*, а
  тот по умолчанию **аварийно завершает процесс** — то есть длинный `%s` в
  `DPRINT` кладёт игру вместо обрезки строки;
* при ошибке кодирования/формата возвращается `-1`, и тогда пишем по индексам
  `-1, 0, 1` — порча стека/памяти вокруг локального буфера.

Проверяйте `if( i < 0 || i > (int)sizeof(format) - 3 ) return;` и используйте
`_vsnprintf_s(format, sizeof(format) - 2, _TRUNCATE, fmt, args)`.

### 4.4 Непроверенные результаты `PatternScan`

* `Source.cpp:179` и `:187`:
  ```cpp
  m_pGlobalVars = **( CGlobalVars*** )( Memory::PatternScan( ... ) + 1 );
  m_pInput      = **( IInput*** )   ( Memory::PatternScan( ... ) + 2 );
  ```
  Если паттерн не найден (патч игры, другой билд клиента, Steam-версия), `PatternScan`
  вернёт `0`, и мы получим `**(T***)(0+1)` — чтение по адресу `0x1`. Проверка
  `if( !m_pGlobalVars )` после этого бесполезна: падает раньше.
* `Hooked.cpp:3428-3432` — пять сигнатур в `static`-инициализаторах без проверки;
  `Hooked_CL_RunPrediction` дергается хуком из движка, т.е. падение будет «где-то в engine.dll».

Правильно: сначала получить адрес, проверить на 0, только потом разыменовывать; при
провале — не ставить хук и аккуратно выгрузиться.

Отдельно: `Source::Startup()` **ставит `CL_RunPrediction`-детур раньше**, чем vmt-хуки
(`Source.cpp:299`), но вызывает `Hooked_CL_RunPrediction`, который дергает
`m_pPrediction->Update(...)` — если по цепочке выше что-то nullptr, получим краш в
самом горячем месте.

### 4.5 `FindVar(...)->m_nValue` без проверки

`Hooked.cpp:1868-1869`, `:1919-1921`, `:2053-2118` (`cl_minmodels`, `net_fakelag`, `sv_cheats`),
`Menu.cpp:941`, `:997` (`cl_mouseenable`). `ICvar::FindVar` возвращает `nullptr`, если
конвара нет (другая версия клиента, кастомный сервер, отключённые cvar'ы) — это
разыменование нуля в каждом тике `CreateMove` и в каждом кадре меню.

Фикс: кэшировать `ConVar*` один раз при `Startup()` (это ещё и минус 3-4 вызова
`FindVar` + расшифровки строки на каждый тик) и проверять на `nullptr` при получении.

### 4.6 Двойной `Eject()` и `Sleep(1000)` под loader lock

`Main.cpp:38` (`Eject`) вызывается по двум путям: из `CheatThread` (`Main.cpp:93`) и из
`DLL_PROCESS_DETACH` (`Main.cpp:129`). При выходе из игры срабатывают оба: поток
выгружается через `FreeLibraryAndExitThread` (что само по себе дергает
`DLL_PROCESS_DETACH`) и одновременно крутится `OnProcessDetach`. Итог — гонка:
`Source::Release()` вызывается дважды, в том числе после `Free()`.

Кроме этого:

* `Sleep(1000)` внутри `Eject()` — а `Eject()` вызывается из `DllMain(DLL_PROCESS_DETACH)`,
  то есть **секунда сна под loader lock**: ОС в это время не может загружать/выгружать
  модули, поток игры стоит.
* Нет проверки `lpReserved` (в `DLL_PROCESS_DETACH` он `NULL` при `FreeLibrary`,
  и не-`NULL` при завершении процесса — во втором случае снимать хуки вообще не нужно
  и опасно, потому что часть модулей движка уже выгружена).
* Нет идемпотентности: флаг «уже выгружаемся» (`std::atomic<bool> m_bEjecting`) отсутствует.

Как правильно: в `DLL_PROCESS_DETACH` — если `lpReserved != nullptr`, ничего не делать;
иначе снять детур/хуки без сна; всю тяжёлую очистку делать в отдельном потоке до выгрузки.

### 4.7 Мусор в `AddressSanitizer`-смысле: `Config::Misc->Crash`

`Hooked.cpp:1793-1867` — три режима, пишущие в `INetChannel` по магическим адресам
(`(int)chan + 68`, vtable-индекс 59, до 200 записей `WriteUBitLong`) напрямую в
буфер исходящих пакетов. Это «краш-чит»: он по определению ломает клиент, а при
неверном смещении/индексе (например, после патча движка) — роняет игру себе же.
Стоит либо убрать, либо спрятать за отдельную сборку и обязательно проверять
`chan != nullptr` и границы буфера (сейчас проверяется только `CrashRestricion`).

### 4.8 `Speed()` — мертвая ветка и мусорный код

`Hooked.cpp:494-540`: `blackcock`, `random == random2`, `float blackcock` во вложенном
блоке, `static float yaw` — состояние живёт между тиками, `srand` не вызывается ни разу
при использовании `rand()`. Функция фактически ничего не делает (локальные переменные),
но вызывается каждый тик. Такое нужно либо удалить, либо переписать честно — сейчас это
«как выглядит движение игрока в дебаггере анти-чита».

### 4.9 Паника (F12) не выключает функционал

`Shared::m_bPanic` проверяется только в отрисовке: `Hooked.cpp:2226` (Reset),
`:2244` (DrawModelEx/chams), `:3386` (PresentProxy). При нажатии паники ESP/меню
исчезают, но **аймбот, триггербот и анти-аим продолжают работать**. Ожидаемое
поведение паник-кея — немедленно прекратить всю активность. Нужно добавить
`if( Shared::m_bPanic ) return;` в начало `Aimbot::OnCreateMove`, `Triggerbot::OnCreateMove`
и в блок анти-аима.

### 4.10 Мелочи того же класса

* `PlayerList.cpp:44-47` — цикл `for( i = 0; i <= GetMaxClients(); i++ )`: и лишний
  индекс 0 (worldspawn), и выход за «легальный» диапазон игроков `0..maxclients-1`.
  Плюс `Player::m_name` **не инициализируется** ни в конструкторе (`PlayerList.cpp:8-16`),
  ни при неудачном `GetPlayerInfo` (`:30-31`) — `strcmp`/ESP читают мусор из стека
  до первого успешного апдейта и после смены карты. Достаточно `m_name[0] = '\0';`
  в конструкторе и в ветке `!m_player`.
* `GetPlayer( int index )` (`PlayerList.cpp:50-53`) отдаёт элемент массива **без
  проверки индекса** — любой вызов с индексом > 64 (или отрицательным) выходит за
  границы `m_players[65]`.
* `Hooked.cpp:1715` — `#include "inetmsghandler.hpp"` **в середине файла**. Это ломает
  порядок зависимостей и вводит в соблазн «инклюднуть что угодно где угодно».
* `Menu.cpp:275` — `const char* nm = XorStr("-")` внутри цикла: `decrypt()` возвращает
  указатель на временный `XorString`, который умирает в конце полного выражения →
  висячий указатель. Сейчас прокатывает за счёт времени жизни временного объекта
  (до конца полного выражения он жив, а `nm` используется дальше) — на грани UB.
  Заведите `std::string` и копируйте туда.

### 5.2 Конфиг: две почти одинаковые структуры + `memcpy` всего состояния каждый тик

`Config.hpp` — `AimbotList` (rage, ~70 полей) и `LegitbotList` (~40 полей, из них
30 дублируются 1:1). `Config::OnCreateMove()` (`Config.cpp:1206-1308`) каждый тик
копирует `memcpy(Current->Aimbot, Main->Aimbot, sizeof(AimbotList))` (и то же для
Triggerbot — вне зависимости от того, менялся конфиг или нет), а затем **руками**
перекладывает 66 полей из `LegitbotList` в `AimbotList` (включая костыль
`iPrioBone[5]`, `Config.cpp:1233`) и **руками** гасит 24 рейдж-поля
(`Config.cpp:1280-1306`, например `Silent`, `HitScan`, `NoSpread`, `Resolver`).

Сама по себе цена `memcpy` невелика, но ручной маппинг — источник «тихих» багов:

### 11.4 «Меню рисуется, но пустое и не работает» — найдено и исправлено

После первой серии правок меню появилось, но по словам пользователя
(«меню поломано, очень поломано, там всё почти не работает») рисовались только
рамка окна, вкладки и левая верхняя панель, а правая часть панелей была пустой
и почти всё не реагировало на мышь. Причина оказалась одна и системная.

| № | Причина | Что сделано |
|---|---|---|
| 1 | **Все панели меню были одним и тем же окном ImGui.** В этой сборке `ImGui::BeginChild()` (ImGui.cpp:3651) собирает имя дочернего окна как `"<имя родителя>.<str_id>"` и вызывает `Begin()` → `FindWindowByName()` (ImGui.cpp:3781), то есть поиск идёт **по строке**, без участия ID-стека (`PushID` в имя не попадает). Все панели использовали `"##c"` → получали одно общее окно. Полная инициализация окна выполняется только при `first_begin_of_the_frame` (ImGui.cpp:4048), поэтому позиция, размер, `ClipRect` и `WindowRectClipped` брались от **первой** панели кадра. Содержимое остальных панелей рисовалось за пределами этого `ClipRect` (отсекалось на отрисовке) и отбрасывалось в `ItemAdd()` (ImGui.cpp:1846: `IsClippedEx` → `return false`), из-за чего элементы ещё и не получали hover/клик. Отсюда ровно наблюдаемая картина: первая панель левой колонки видна и работает, все остальные «пустые и мёртвые»; вкладки (они в родительском окне) при этом переключались | `AW::BeginPanel` формирует уникальное имя дочернего окна: `sprintf_s(szPanelId, "##panel_%d_%d_%s", (int)p.x, (int)p.y, title)`. Имя уникально внутри кадра и стабильно между кадрами (позиции панелей — константные смещения от центра окна), поэтому лишние окна не создаются |
| 2 | `AW::SliderInt` рисуется через `SliderFloat`, а тот печатает значение как `float` (`sprintf_s(..., fmt, *v)`). Форматы вида `"%d ms"` и `"%d%%"` подставляли float под `%d`, а `"%.0f%%"` — целое под `%f`: неопределённое поведение и мусор в подписи слайдера (RCS Amount X/Y, Flash Amount, Refire Delay) | В `SliderInt` добавлено преобразование формата: `%d`/`%i` → `%.0f` (с учётом `%%` и текста вокруг), плюс пять мест с `"%.0f%%"` у int-слайдеров переведены на `"%d%%"` |
| 3 | Клик мимо элементов (по шапке панели, по промежутку между панелями, по пустому месту внутри панели) переводил окно в режим перетаскивания: `EndFrame()` (ImGui.cpp:2588) выставлял `MovedWindow` и `ActiveId = MoveID`. Пока кнопка мыши удерживалась, `ItemAdd`/`IsHovered` не отдавали hover ни одному элементу (ActiveId занят), а следующем кадре `g.HoveredWindow` принудительно становился перемещаемым окном. В этой сборке `BeginChild()` **не** выставляет `NoMove` (в стоковом ImGui 1.49 он есть, там же есть и в `BeginChildFrame`), и у главного окна меню `NoMove` тоже не было | `ImGuiWindowFlags_NoMove` добавлен: панелям (`BeginChild`), списку в выпадающем комбобоксе (`##rows`) и главному окну `mainmenu`. Позиция меню и так задаётся каждый кадр через `SetNextWindowPos`, так что перетаскивание было бессмысленным |

**Как проверить, что это именно тот баг:** если рамки/заголовки панелей
(«Aimbot», «Triggerbot», «Filter») рисуются, а их содержимое — нет, значит
`ClipRect` дочернего окна не совпадает с панелью; после исправления каждая
панель имеет собственное окно `##panel_<x>_<y>_<title>`.

Проверено статически (компилятора MSVC на машине нет): баланс скобок в
`Menu.cpp` — `{}` 187/187, `()` 1825/1825, `[]` 197/197; все пары
`BeginChild/EndChild`, `BeginPanel/EndPanel`, `PushStyle*/PopStyle*`,
`PushID/PopID`, `PushFont/PopFont` в файле сходятся.
