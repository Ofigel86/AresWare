# Анализ проекта AresWare (internal-чит для CS: Source v34)

Статический анализ кода (Windows/MSVC-сборку в этой среде выполнить нельзя, поэтому все
выводы — из чтения исходников). Ссылки даны в формате `файл:строка`.

---

## 1. Краткое резюме

Проект — зрелый по функциональности, но «перегруженный» internal-чит: 7 вкладок меню,
ragebot/legitbot, резолвер, анти-аим, lag-компенсация, ESP/chams, триггербот, конфиги
на оружие. Архитектура в целом правильная (интерфейсы движка → хуки → фичи → UI),
но есть **несколько багов, которые прямо ведут к падению игры**, и заметный
технический долг: 3.5-тысячестрочный `Hooked.cpp`, дублирующиеся конфиг-структуры,
скопированный шесть раз код обработки клавиш, ~1.2 ГБ вендорных исходников в git.

| Метрика | Значение |
|---|---|
| Свои исходники (без ImGui/stb/ассетов) | **22 125 строк**, 60 файлов |
| Самые крупные свои файлы | `Hooked.cpp` 3580, `Valve.hpp` 2249, `Menu.cpp` 2093, `Config.cpp` 1395, `Aimbot.cpp` 1143, `Resolver.cpp` 1012 |
| Вендорное/данные | `Sounds.cpp` 27 730 строк (MP3-массивы), `ImGui.cpp` 10 250 (1.49), `picture.hpp` 4342 (PNG), `MenuIcons.hpp` 625 |

| Конфигурации | `Debug`/`Home` → `v34.dll`, `Release` → `release.dll` |

## 2. Архитектура

### 2.1 Карта слоёв

```

  ├─ Memory.hpp/.cpp      PatternScan, VCall, Safe* helpers
```

## 3. Что сделано хорошо

1. **Разделение слоёв и абстракции хуков.** `VmtSwap` с backup-vtable + `Detour` с
   backup-кодом, `ScopedMemProtect` (RAII над `VirtualProtect`) — аккуратно.
2. **Обфускация строк** `XorStr` (`Crypt.hpp:117`) — компайл-тайм XOR, ~1400 использований.
   Для internal-чита это базовый must-have, и он есть.
3. **Отсутствие внешних зависимостей**, кроме `d3dx9.lib`: всё вкомпилировано
   (звуки хитмаркера, PNG-иконки меню, шрифты) — DLL самодостаточна.
4. **Динамический резолв API** (`ModuleD`/`GetProcedure`, `Valve.cpp`) вместо IAT — скрывает
   импорты от статического анализа.
5. **Правильные примитивы синхронизации между потоками** — `std::atomic` в `Shared.hpp`,
   команды Load/Save через флаги, а не через прямой вызов из WndProc.
6. **Документирование сложных мест.** `Aimbot.hpp` — образец: каждый приватный метод
   подписан комментарием по-русски. `Resolver.cpp`, `LagCompensation.hpp`,
   `Accuracy.cpp:31-39` — тоже с объяснением «почему именно так».
7. **Защита от NaN/Inf** (`Hooked.cpp:227 IsBadFloat` + `AntiSMAC`) — сетевые проверки
   на бреде в углах сервер ловит, это правильно.
8. **Валидация конфига** — `Clamp()` у каждой структуры, `LimitValue` на загрузке.
9. **Обработка исключений вокруг хуков** (`__try/__except` в `CreateMove`,
   `FrameStageNotify`, `PresentProxy`) — в internal-чите это обязательный минимум.
10. **Лицензия по умолчанию выключена** и корректно реализована: при провале проверки
    `DllMain` возвращает `FALSE`, загрузчик сам выгружает DLL, игра не трогается.

## 4. P0 — баги, которые ведут к падению/некорректной работе

### 4.1 `Memory::SafeDelete/SafeReset/SafeRelease` — молча не работают

`Memory.hpp:40`, `:58`, `:67` — параметр принимается **по значению**:

```cpp
template< typename T >
inline void SafeDelete( T object )   // <-- копия указателя
{
    if( object ) delete object;
    object = nullptr;   // обнуляется локальная копия
}
```

Следствие: в `Config::Release()` (`Config.cpp:70-96`) и `Source::Free()`
(`Source.cpp:449+`) **ни один объект реально не удаляется**, указатели в
`Config::Main/ESP/...` остаются валидными (dangling-подобное состояние: память жива,
но считалась освобождённой логикой). В `VmtSwap`/`Detour` (`make_unique`, `shared_ptr`)
это не проблема, а вот `new`-структуры конфига утекают и второй вызов `Release()`
(теоретически возможный при двойном Eject) будет двойным `delete`.

Лечение — по ссылке:

```cpp
template< typename T > inline void SafeDelete( T& object )  { if( object ) { delete object;    object = nullptr; } }
template< typename T > inline void SafeDeleteArray( T& o )  { if( o )      { delete[] o;        o = nullptr; } }
template< typename T > inline void SafeReset( T& o )        { if( o )      { o.reset();         o = nullptr; } }
template< typename T > inline void SafeRelease( T& o )      { if( o )      { o->Release();      o = nullptr; } }
```

Дополнительно: `Config::Release()` разыменовывает `Main`/`Current` без проверки на
`nullptr` — при частично провалившемся `Startup()` это краш. Добавьте `if( !Main ) return;`
и обнуляйте `Weapon[i] = nullptr;` (сейчас массив остаётся с висящими указателями).

### 4.2 `VmtSwap::Release()` → `Restore()` без проверки, что `Apply()` вообще прошёл

`VmtSwap.cpp:39-53`: `Release()` безусловно вызывает `Restore()`, а тот пишет
`*m_ppInstance = m_pBackupVmt;`, где `m_ppInstance == nullptr`, если `Apply()` не
вызывался или упал на первой проверке (`VmtSwap.cpp:22`: `if( !pInstance )` — а
`Apply` может упасть и на `m_pCustomVmt`).

Сценарий краша (реальный, не теоретический): `Source::Startup()` устанавливает часть
хуков, затем что-то не находит (сигнатура/cvar/шрифт) → `return false` → `Main.cpp:69`
`Eject()` → `Source::Release()` → `m_pClientSwap->Release()`. Если к этому моменту
`Apply()` у какого-то свапа не прошёл — гарантированный Access Violation **в момент
выгрузки**, то есть чит «роняет игру при неудачной инжекции».

Минимальный фикс: в `Restore()` — `if( !m_ppInstance || !m_pBackupVmt ) return;`,
в `Hook()` — `if( nIndex >= m_nSize ) return;` (сейчас `VmtSwap.cpp:56-59` пишет
в массив без проверки индекса — одна опечатка в индексе = перезапись чужой памяти).

### 4.3 `Debug::Print` пишет за границы буфера

`Debug.cpp:15-20`:

```cpp
int i = vsprintf_s( format, sizeof( format ), fmt, args );
format[ i + 0 ] = '\r';
format[ i + 1 ] = '\n';
format[ i + 2 ] = '\0';   // при i >= 2046 — выход за пределы
```

Две проблемы разом:

* при нехватке места в буфере `vsprintf_s` вызывает *invalid parameter handler*, а
  тот по умолчанию **аварийно завершает процесс** — то есть длинный `%s` в
  `DPRINT` кладёт игру вместо обрезки строки;
* при ошибке кодирования/формата возвращается `-1`, и тогда пишем по индексам
  `-1, 0, 1` — порча стека/памяти вокруг локального буфера.

Проверяйте `if( i < 0 || i > (int)sizeof(format) - 3 ) return;` и используйте
`_vsnprintf_s(format, sizeof(format) - 2, _TRUNCATE, fmt, args)`.

### 4.4 Непроверенные результаты `PatternScan`

* `Source.cpp:179` и `:187`:
  ```cpp
  m_pGlobalVars = **( CGlobalVars*** )( Memory::PatternScan( ... ) + 1 );
  m_pInput      = **( IInput*** )   ( Memory::PatternScan( ... ) + 2 );
  ```
  Если паттерн не найден (патч игры, другой билд клиента, Steam-версия), `PatternScan`
  вернёт `0`, и мы получим `**(T***)(0+1)` — чтение по адресу `0x1`. Проверка
  `if( !m_pGlobalVars )` после этого бесполезна: падает раньше.
* `Hooked.cpp:3428-3432` — пять сигнатур в `static`-инициализаторах без проверки;
  `Hooked_CL_RunPrediction` дергается хуком из движка, т.е. падение будет «где-то в engine.dll».

Правильно: сначала получить адрес, проверить на 0, только потом разыменовывать; при
провале — не ставить хук и аккуратно выгрузиться.

Отдельно: `Source::Startup()` **ставит `CL_RunPrediction`-детур раньше**, чем vmt-хуки
(`Source.cpp:299`), но вызывает `Hooked_CL_RunPrediction`, который дергает
`m_pPrediction->Update(...)` — если по цепочке выше что-то nullptr, получим краш в
самом горячем месте.

### 4.5 `FindVar(...)->m_nValue` без проверки

`Hooked.cpp:1868-1869`, `:1919-1921`, `:2053-2118` (`cl_minmodels`, `net_fakelag`, `sv_cheats`),
`Menu.cpp:941`, `:997` (`cl_mouseenable`). `ICvar::FindVar` возвращает `nullptr`, если
конвара нет (другая версия клиента, кастомный сервер, отключённые cvar'ы) — это
разыменование нуля в каждом тике `CreateMove` и в каждом кадре меню.

Фикс: кэшировать `ConVar*` один раз при `Startup()` (это ещё и минус 3-4 вызова
`FindVar` + расшифровки строки на каждый тик) и проверять на `nullptr` при получении.

### 4.6 Двойной `Eject()` и `Sleep(1000)` под loader lock

`Main.cpp:38` (`Eject`) вызывается по двум путям: из `CheatThread` (`Main.cpp:93`) и из
`DLL_PROCESS_DETACH` (`Main.cpp:129`). При выходе из игры срабатывают оба: поток
выгружается через `FreeLibraryAndExitThread` (что само по себе дергает
`DLL_PROCESS_DETACH`) и одновременно крутится `OnProcessDetach`. Итог — гонка:
`Source::Release()` вызывается дважды, в том числе после `Free()`.

Кроме этого:

* `Sleep(1000)` внутри `Eject()` — а `Eject()` вызывается из `DllMain(DLL_PROCESS_DETACH)`,
  то есть **секунда сна под loader lock**: ОС в это время не может загружать/выгружать
  модули, поток игры стоит.
* Нет проверки `lpReserved` (в `DLL_PROCESS_DETACH` он `NULL` при `FreeLibrary`,
  и не-`NULL` при завершении процесса — во втором случае снимать хуки вообще не нужно
  и опасно, потому что часть модулей движка уже выгружена).
* Нет идемпотентности: флаг «уже выгружаемся» (`std::atomic<bool> m_bEjecting`) отсутствует.

Как правильно: в `DLL_PROCESS_DETACH` — если `lpReserved != nullptr`, ничего не делать;
иначе снять детур/хуки без сна; всю тяжёлую очистку делать в отдельном потоке до выгрузки.

### 4.7 Мусор в `AddressSanitizer`-смысле: `Config::Misc->Crash`

`Hooked.cpp:1793-1867` — три режима, пишущие в `INetChannel` по магическим адресам
(`(int)chan + 68`, vtable-индекс 59, до 200 записей `WriteUBitLong`) напрямую в
буфер исходящих пакетов. Это «краш-чит»: он по определению ломает клиент, а при
неверном смещении/индексе (например, после патча движка) — роняет игру себе же.
Стоит либо убрать, либо спрятать за отдельную сборку и обязательно проверять
`chan != nullptr` и границы буфера (сейчас проверяется только `CrashRestricion`).

### 4.8 `Speed()` — мертвая ветка и мусорный код

`Hooked.cpp:494-540`: `blackcock`, `random == random2`, `float blackcock` во вложенном
блоке, `static float yaw` — состояние живёт между тиками, `srand` не вызывается ни разу
при использовании `rand()`. Функция фактически ничего не делает (локальные переменные),
но вызывается каждый тик. Такое нужно либо удалить, либо переписать честно — сейчас это
«как выглядит движение игрока в дебаггере анти-чита».

### 4.9 Паника (F12) не выключает функционал

`Shared::m_bPanic` проверяется только в отрисовке: `Hooked.cpp:2226` (Reset),
`:2244` (DrawModelEx/chams), `:3386` (PresentProxy). При нажатии паники ESP/меню
исчезают, но **аймбот, триггербот и анти-аим продолжают работать**. Ожидаемое
поведение паник-кея — немедленно прекратить всю активность. Нужно добавить
`if( Shared::m_bPanic ) return;` в начало `Aimbot::OnCreateMove`, `Triggerbot::OnCreateMove`
и в блок анти-аима.

### 4.10 Мелочи того же класса

* `PlayerList.cpp:44-47` — цикл `for( i = 0; i <= GetMaxClients(); i++ )`: и лишний
  индекс 0 (worldspawn), и выход за «легальный» диапазон игроков `0..maxclients-1`.
  Плюс `Player::m_name` **не инициализируется** ни в конструкторе (`PlayerList.cpp:8-16`),
  ни при неудачном `GetPlayerInfo` (`:30-31`) — `strcmp`/ESP читают мусор из стека
  до первого успешного апдейта и после смены карты. Достаточно `m_name[0] = '\0';`
  в конструкторе и в ветке `!m_player`.
* `GetPlayer( int index )` (`PlayerList.cpp:50-53`) отдаёт элемент массива **без
  проверки индекса** — любой вызов с индексом > 64 (или отрицательным) выходит за
  границы `m_players[65]`.
* `Hooked.cpp:1715` — `#include "inetmsghandler.hpp"` **в середине файла**. Это ломает
  порядок зависимостей и вводит в соблазн «инклюднуть что угодно где угодно».
* `Menu.cpp:275` — `const char* nm = XorStr("-")` внутри цикла: `decrypt()` возвращает
  указатель на временный `XorString`, который умирает в конце полного выражения →

  (до конца полного выражения он жив, а `nm` используется дальше) — на грани UB.
  Заведите `std::string` и копируйте туда.

### 5.2 Конфиг: две почти одинаковые структуры + `memcpy` всего состояния каждый тик

`Config.hpp` — `AimbotList` (rage, ~70 полей) и `LegitbotList` (~40 полей, из них
30 дублируются 1:1). `Config::OnCreateMove()` (`Config.cpp:1206-1308`) каждый тик
копирует `memcpy(Current->Aimbot, Main->Aimbot, sizeof(AimbotList))` (и то же для
Triggerbot — вне зависимости от того, менялся конфиг или нет), а затем **руками**
перекладывает 66 полей из `LegitbotList` в `AimbotList` (включая костыль
`iPrioBone[5]`, `Config.cpp:1233`) и **руками** гасит 24 рейдж-поля
(`Config.cpp:1280-1306`, например `Silent`, `HitScan`, `NoSpread`, `Resolver`).

Сама по себе цена `memcpy` невелика, но ручной маппинг — источник «тихих» багов:

### 11.4 «Меню рисуется, но пустое и не работает» — найдено и исправлено

После первой серии правок меню появилось, но по словам пользователя
(«меню поломано, очень поломано, там всё почти не работает») рисовались только
рамка окна, вкладки и левая верхняя панель, а правая часть панелей была пустой
и почти всё не реагировало на мышь. Причина оказалась одна и системная.

| № | Причина | Что сделано |
|---|---|---|
| 1 | **Все панели меню были одним и тем же окном ImGui.** В этой сборке `ImGui::BeginChild()` (ImGui.cpp:3651) собирает имя дочернего окна как `"<имя родителя>.<str_id>"` и вызывает `Begin()` → `FindWindowByName()` (ImGui.cpp:3781), то есть поиск идёт **по строке**, без участия ID-стека (`PushID` в имя не попадает). Все панели использовали `"##c"` → получали одно общее окно. Полная инициализация окна выполняется только при `first_begin_of_the_frame` (ImGui.cpp:4048), поэтому позиция, размер, `ClipRect` и `WindowRectClipped` брались от **первой** панели кадра. Содержимое остальных панелей рисовалось за пределами этого `ClipRect` (отсекалось на отрисовке) и отбрасывалось в `ItemAdd()` (ImGui.cpp:1846: `IsClippedEx` → `return false`), из-за чего элементы ещё и не получали hover/клик. Отсюда ровно наблюдаемая картина: первая панель левой колонки видна и работает, все остальные «пустые и мёртвые»; вкладки (они в родительском окне) при этом переключались | `AW::BeginPanel` формирует уникальное имя дочернего окна: `sprintf_s(szPanelId, "##panel_%d_%d_%s", (int)p.x, (int)p.y, title)`. Имя уникально внутри кадра и стабильно между кадрами (позиции панелей — константные смещения от центра окна), поэтому лишние окна не создаются |
| 2 | `AW::SliderInt` рисуется через `SliderFloat`, а тот печатает значение как `float` (`sprintf_s(..., fmt, *v)`). Форматы вида `"%d ms"` и `"%d%%"` подставляли float под `%d`, а `"%.0f%%"` — целое под `%f`: неопределённое поведение и мусор в подписи слайдера (RCS Amount X/Y, Flash Amount, Refire Delay) | В `SliderInt` добавлено преобразование формата: `%d`/`%i` → `%.0f` (с учётом `%%` и текста вокруг), плюс пять мест с `"%.0f%%"` у int-слайдеров переведены на `"%d%%"` |
| 3 | Клик мимо элементов (по шапке панели, по промежутку между панелями, по пустому месту внутри панели) переводил окно в режим перетаскивания: `EndFrame()` (ImGui.cpp:2588) выставлял `MovedWindow` и `ActiveId = MoveID`. Пока кнопка мыши удерживалась, `ItemAdd`/`IsHovered` не отдавали hover ни одному элементу (ActiveId занят), а следующем кадре `g.HoveredWindow` принудительно становился перемещаемым окном. В этой сборке `BeginChild()` **не** выставляет `NoMove` (в стоковом ImGui 1.49 он есть, там же есть и в `BeginChildFrame`), и у главного окна меню `NoMove` тоже не было | `ImGuiWindowFlags_NoMove` добавлен: панелям (`BeginChild`), списку в выпадающем комбобоксе (`##rows`) и главному окну `mainmenu`. Позиция меню и так задаётся каждый кадр через `SetNextWindowPos`, так что перетаскивание было бессмысленным |

| 4 | Курсор меню (`io.MousePos`) заполняется только сообщениями `WM_MOUSEMOVE` (ImGuiDX9.cpp), а до первого движения мыши в ImGui лежит `-FLT_MAX`, либо координаты с прошлого открытия меню. В первый кадр после открытия не работает ни один элемент («пока мышью не пошевелишь — мертво»), а если сообщения до окна не доходят (raw input, пересозданное при смене разрешения окно) — курсор «залипает» навсегда | Позиция курсора синхронизируется с системной (`GetCursorPos` + `ScreenToClient` + `GetClientRect`) — но только когда пригодного значения в ImGui нет (кадр открытия меню или отрицательные координаты), так что живой ввод это не перебивает. Для этого `Menu` запоминает `HWND` из `Create()` |
| 5 | В `io` оставалось состояние с прошлого открытия меню: `OnKeyEvent` вызывается только при открытом меню, поэтому «зажатая» до этого клавиша подхватывалась как бинд сразу при повторном открытии, а незавершённый захват клавиши (`s_pKeyCap`) ждал первого нажатия | При закрытии меню сбрасываются `io.KeysDown`, `io.MouseDown` и незавершённый захват клавиши |

**Как проверить, что это именно тот баг:** если рамки/заголовки панелей
(«Aimbot», «Triggerbot», «Filter») рисуются, а их содержимое — нет, значит
`ClipRect` дочернего окна не совпадает с панелью; после исправления каждая
панель имеет собственное окно `##panel_<x>_<y>_<title>`.

Проверено статически (компилятора MSVC на машине нет): баланс скобок в
`Menu.cpp` — `{}` 197/197, `()` 1847/1847, `[]` 207/207; все пары
`BeginPanel/EndPanel` (29/29), `BeginChild/EndChild` (2/2), `PushStyle*/PopStyle*`,
`PushID/PopID`, `PushFont/PopFont` (2/2) в файле сходятся.

Дополнительно проверено по коду этой сборки ImGui: у виджетов ID считается от
ID окна (`ImGuiWindow::GetID` → `IDStack.back()`, а `IDStack[0] = ImHash(имя
окна)`), поэтому уникальные имена панелей заодно убрали и коллизии ID: раньше
одноимённые элементы в разных панелях (`Delay`, `Target`, `Min Damage`, чекбоксы
`Head`/`Arms`) имели один и тот же ID — при перетаскивании слайдера в одной
панели одновременно менялся его «двойник» в другой. Это тоже следствие общей
панели-окна и лечится тем же фиксом.

Что осталось непроверяемым здесь: поведение в игре (нет ни компилятора, ни
игры). Если после сборки что-то из меню всё ещё ведёт себя странно — нужен
скриншот и `C:\rraggerr\v34\aresware.log`.

## 11.6. Аудит рейдж-пути (сборка после C2039)

Жалоба «есть баги и ошибки в рейдж боте» проверялась статически по всему
рейдж-пути: `Config::OnCreateMove` → `Aimbot::OnCreateMove` → хитскан/прострел
→ `Resolver` → `LagCompensation` → `Hooked::CreateMove` (AA/чок).

### Найдено и исправлено

1. **Выход за границы в backtracking (`LagCompensation.cpp`).**
   `std::memcpy(&backup_layers_update[i], player->GetAnimOverlays(),
   sizeof(C_AnimationLayer) * player->GetNumAnimOverlays())`, где приёмник —
   `static C_AnimationLayer backup_layers_update[65][15]`, а
   `GetNumAnimOverlays()` отдаётся игрой из сети без ограничения. Значение
   больше 15 писало за конец массива (порча статики чита), значение 0 или
   нулевой указатель слоёв — `memcpy` по `nullptr`. Исправлено в источнике
   (`C_BaseEntity::GetNumAnimOverlays()` теперь ограничивает 0..15 и проверяет
   указатель), плюс проверки перед `memcpy` и `continue` при отсутствии слоёв.
2. **`C_BaseEntity::GetAnimOverlay(index)`** — было `&layers[index]` без
   проверок: нулевой указатель или индекс за концом массива слоёв.
3. **Индекс игрока в `LagCompensation`**: `m_LagRecord[player->GetIndex() - 1]`
   (`std::array<..., 64>`) во всех десяти функциях — без проверки. Индекс
   приходит из виртуального вызова движка; мусорный индекс = произвольная
   запись по памяти на каждом кадре. Добавлена проверка `0 <= index < 64` и
   `player != nullptr` в начале каждой функции.
4. **`GetMaxClients()` как граница циклов.** Значение из движка может быть
   больше 64 (кастомные серверы, момент смены карты), а таблицы чита рассчитаны
   на 64 игрока. Добавлен `Source::MaxClients()` (клампит до 64 и проверяет
   указатель на движок); все циклы по игрокам в `Hooked.cpp`, `Aimbot.cpp`,
   `LagCompensation.cpp`, `Menu.cpp`, `PlayerList.cpp` переведены на него.
5. **`Config::OnCreateMove` — `Weapon[ i ]` без проверок.** `i` —
   `GetWeaponID()` активного оружия. При `WEAPON_NONE`/id вне `WEAPON_MAX`
   (новое оружие, кастомный сервер) читался указатель за границей массива и
   выполнялся `memcpy` из мусора; при пустом слоте — разыменование `nullptr`.
   Теперь индекс и все три указателя проверяются, при провале используется
   общий конфиг (как при выключенном Weapon Config) + одна запись в лог.
6. **То же при загрузке/сохранении конфига** (`Config.cpp`): цикл по
   `WeaponList` обращался к `Weapon[ index ]->Aimbot->...` без проверок —
   битое имя оружия или неудачная аллокация валили чит прямо при старте.
   Добавлена общая проверка и `continue`.
7. **`Feature::Accuracy::CanPenetrate` — `GetSurfaceData()` без проверки.**
   Результат движка разыменовывался как `pSurfaceData->game.material` (и в
   теле цикла, и при выходе из прострела). Добавлен хелпер
   `MaterialOfSurface()`: при `nullptr` берётся `CHAR_TEX_CONCRETE`
   (самые консервативные параметры пробития) — расчёт остаётся честным,
   падения нет.
8. **Висячий `if` в `Hooked::CreateMove` (регрессия этой ветки).**
   Перед `if (Config::Removals->NoRecoil)` стояло условие анти-аима без тела,
   поэтому компенсация отдачи включалась только при включённом AA. Условие
   разделено: `if (!Shared::m_bPanic && Config::Removals->NoRecoil)`.
9. **Меню, вкладки Ragebot/Legitbot — `Config::Weapon[ wid ]` без проверки.**
   `GetWeaponID()` может вернуть `WEAPON_NONE`, а слот — не выделиться: это
   разыменование мусора в кадре отрисовки. Добавлен `AW::WeaponSlot()` и
   защита в `DrawAimbotBlock`/`DrawTriggerBlock` (`if (!ptr) return;`).
10. **`Config::MiscList::Clamp()`** — `FakePing` не ограничивался, а значение
    пишется прямо в `net_fakelag`: конфиг с большим числом уводил клиента в
    бесконечный choke до кика с сервера. Добавлен `LimitValue(FakePing, 0, 260)`.

### Проверено и признано корректным (не переделывать)

* индексация `WeaponList[24]` → `GetWeaponID` → `Weapon[]`: все 24 имени дают

Статический аудит закрывает падения и заведомо неверную логику, но какие
именно симптомы «багов рейджбота» видны в игре (не стреляет / не попадает /
AA не работает / крашится) — нужно уточнить: часть поведения зависит от
настроек конфига и от сервера, а не от кода.

## 11.7. Второй раунд по жалобам: меню, рейджбот, анти-аим

Из ответов пользователя: «аа сломаны, а рейджбот даже не стреляет», «левая
вкладка анти-аимов в рейджботе — настройки слонялись», «не работал скрол»,
«почему-то настройки из легит бота в рейджботе». Плюс «Weapon Config: включён».

### 1. Скролл меню — подтверждено харнессом

`AW::BeginPanel` вычитает `ImGui::GetScrollY()`. Тест `dev-harness/scroll_test.cpp`
(панель 380x200, 30 строк, колесо над панелью):

| величина | до | после |
|---|---|---|
| `scrollY` | 0 | 610 |
| `sizeContents.y` | 784 → **растёт от прокрутки** | 784 (не меняется) |
| min Y вершин контента | 126 → **не двигается** | −477.5 |

То есть колесо доходит до панели, содержимое едет вверх, ползунок не «убегает».

### 2. Панели Ragebot → Anti-Aim: «настройки слонялись»

Панель «Aimbot» рисовалась всегда — `(pos.x+14, pos.y+70, 380x582)`, а в
под-вкладке Anti-Aim на том же месте стоят «Stand» `(14,100,380x268)` и
«Move» `(14,376,380x276)`. Две панели ложились друг на друга: визуально
накладывались строки и ползунки прокрутки, а по клику в левой колонке
срабатывали виджеты то одной, то другой панели.

Правка: панель «Aimbot» рисуется только в под-вкладке Weapons; в Anti-Aim
левая колонка целиком отдана Stand/Move, а выбор стиля Rage/Legit вынесен в
строку заголовка (как «Active» во вкладке Legitbot).

Проверка геометрии (скрипт, прямоугольники в пикселях от позиции окна):

* Ragebot/Anti-Aim **до**: 2 пересечения (Aimbot ↔ Stand, Aimbot ↔ Move);
* Ragebot/Anti-Aim **после**: 0 пересечений;
* Ragebot/Weapons, Legitbot: 0 пересечений (не затронуты).

### 3. «Рейджбот даже не стреляет» при включённом «Weapon Config»

В бою используется не общий конфиг, а слот оружия
(`Config::OnCreateMove` → `memcpy(Current->Aimbot, Weapon[i]->Aimbot, ...)`).
В файле конфига у каждого оружия лежал `aimbot.mode = 0` (Off) — это значение
и работало, хотя пользователь настраивал общий конфиг в меню. Тогда же панель
«<оружие> Settings» была пустой (баг совпадающих имён дочерних окон из §11.4),
то есть настроить оружие было вообще нельзя.

Правки:

* загрузка: слот оружия сначала заполняется общим конфигом
  (`memcpy(Weapon[i]->Aimbot, Main->Aimbot, ...)`), после чего читаются
  per-weapon ключи — теперь через `LoadIntDef/LoadBoolDef/LoadFloatDef`
  (добавлен `LoadFloatDef`), т. е. отсутствующий ключ оставляет значение
  общего конфига (53 строки);
* маркер `configured=1` (пишется в `Save`, читается в `Load`): «настраивали»
  и «намеренно Off» больше не одно и то же — оружие без маркера с `Mode = Off`
  при включённом общем режиме наследует общий конфиг (в лог одна строка);
* в панели «Aimbot» при включённом Weapon Config появилась подсказка
  «Weapon Config is on: the right panel is used».

### 4. «Настройки из легит бота в рейджботе»

Проверил: `Config::Legitbot` — это только указатель на выбранный класс для
вкладки Legitbot, в бой он не попадает; легитные значения уходят в
`Config::Current->Aimbot` в `Config::OnCreateMove` (при `AimbotStyle == 1`), а
панели вкладки Ragebot редактируют `Config::Main->Aimbot` (общий) или
`Config::Weapon[]->Aimbot` (per-weapon). То есть данные не пересекаются.

Практическая причина путаницы — та же, что в п. 3: при включённом Weapon
Config правит боем не та панель, которую видно, а при `Style = Legit` рейдж
выключен целиком («Rage inactive: Legit style selected»). Оба состояния теперь
видны прямо в панели и в строке заголовка под-вкладки Anti-Aim.

### 5. Анти-аим: что проверено

Просмотрены `AntiAim()` (питчи/йо-режимы Stand/Move, manual AA, fake duck,
BreakLC, DefensiveChoke), гейты вызова в `CreateMove`, `IsEveryoneDead1..3`,
`AtTarget`, `Config::AntiAimList::Clamp()`, порядок `bSendPacket` (читается из
`bl` на входе нативного CreateMove и пишется обратно), конфликт с
`FakeLag`/`FakeWalk`/`PerfectSilent`. Гейты корректны: «0 = Off» у всех
режимов, `Clamp()` не сбрасывает выбранные режимы (клампятся только скорости,
задержки и клавиши), клип списков не мешает. Отдельного дефекта в самой логике
AA не найдено — в меню же настройки AA были недоступны/наложены (п. 2), что и
выглядело как «АА сломаны».

Если после пересборки AA всё ещё ведут себя неверно — нужен конкретный режим
(Stand/Move, какой именно yaw/pitch) и что видно со стороны (модель не
разворачивается / десинка нет / после выстрела кикает).

## 11.8. C3861: IM_ARRAYSIZE (следующая ошибка сборки)

Отчёт пользователя:

```
Ошибка C3861  IM_ARRAYSIZE: идентификатор не найден
Counter-Strike Source v34\Menu.cpp  1159, 1162
```

Причина: в форке `IM_ARRAYSIZE` объявлен только в `ImGuiInternal.hpp`
(`ImGuiInternal.hpp:78`), а `Menu.cpp` подключает лишь `ImGui.hpp`. Оригинальный
ImGui объявляет этот хелпер в `imgui.h`, поэтому код, написанный «по мотивам»,
на него опирался.

Правки:

* `Menu.cpp` — оба цикла очистки `io.KeysDown`/`io.MouseDown` используют
  `(int)ARRAYSIZE(...)` из `windows.h` (в файле уже 49 таких обращений);
* `ImGui.hpp` — `#ifndef IM_ARRAYSIZE / #define ... / #endif` (как в
  оригинальном `imgui.h`), а в `ImGuiInternal.hpp` то же определение обёрнуто в
  `#ifndef`, чтобы не было C4005 при повторном определении. Теперь любой файл,
  подключающий `ImGui.hpp`, видит `IM_ARRAYSIZE`.

Проверено: Linux-харнесс пересобран с новыми заголовками — `ImGui.cpp`,
`ImGuiDraw.cpp` и тесты (`menu_repro` — 6 списков отрисовки, `scroll_test` —
прокрутка/стабильный `SizeContents`) собираются и проходят.

### Автопроверки этого класса ошибок

Чтобы не собирать проект «по одной ошибке», добавлены два статических
анализатора (лежат в `dev-harness/`, вне репозитория):

* `check_undeclared.py` — строит транзитивное замыкание `#include` для каждого
  `.cpp` и ищет ALL_CAPS-идентификаторы, которые используются как макрос, но не
  объявлены ни в подключённых заголовках, ни в whitelist Windows/D3D API.
  Именно так ловится случай `IM_ARRAYSIZE`. Текущий результат: **OK**;
* `check_members.py` — проверяет `Config::X`, `Source::X`, `AW::X` и вызовы
  `Source::m_pX->метод(...)` против объявлений в заголовках (класс ошибок
  C2039/C3861, к которому относился и предыдущий отчёт про `EnsureCaptured`).
  Текущий результат: **OK** (единственные совпадения — `Source::NetVarManager`
  как имя типа, объявленного в `NetVarManager.hpp`).

## 11.9. Логика аимбота: разбор и исправления

Полный проход по `Aimbot.cpp` (конвейер `OnCreateMove` → `ChangeTarget` →
`IsTargetGood` → `ComputeAimPoint`/`CanHitPoint` → доводка углов → огонь).
Найдено девять логических дефектов; все исправлены.

### 11.9.1 Захваченная цель не перепроверялась на смерть

`m_pTarget` — сырой указатель. После смерти игрока или ухода в дормант он
остаётся валидным, а `IsTargetGood` вызывался уже **после** `ChangeTarget()`,
который при `m_bChangeTarget == false` вообще не запускался. Аимбот мог
«держать» труп до тех пор, пока что-то другое не сбросит флаг.

Добавлена быстрая проверка `IsTargetAlive()` перед выбором цели: не найдена
живой — цель отпускается и запускается поиск.

### 11.9.2 Перебор целей затирал кэш точки прицеливания

`IsTargetGood()` пишет точку в общее поле `m_vTarget`. В `ChangeTarget()` он
вызывается для **каждого** кандидата, поэтому после неудачного перебора в
`m_vTarget` оставалась точка последнего отвергнутого игрока — и следующий тик
целился именно туда. Теперь значения `m_pTarget`/`m_vTarget` сохраняются до
перебора и восстанавливаются, если цель не найдена.

### 11.9.3 `m_Timer` сбрасывался при каждом перезахвате той же цели

`ChangeTarget()` звал `m_Timer.Reset()` безусловно, а таймер обслуживает сразу
`Delay`, `Duration` и `SwitchDelay`. При постоянном перезахвате одной и той же
цели `Elapsed()` почти всегда оказывался меньше `Delay` — **аимбот с задержкой
не доводился вообще**, а `Duration` не истекал никогда. Теперь сброс только при
реальной смене цели; гуманизация задержки (`HumanizeDelay`) пересчитывается там
же, а не каждый тик.

### 11.9.4 `Duration` выключал аимбот навсегда

По истечении `Duration` стоял голый `return`: цель оставалась захваченной, и
аимбот больше не наводился ни на неё, ни на кого-либо ещё. Теперь цель
отпускается (если не включён `NoSwitch`), а отсчёт ведётся от конца `Delay` —
иначе конфигурация `Duration < Delay` не давала ни одного тика доводки.

### 11.9.5 `SwitchDelay` считался от захвата, а не от потери цели

Сравнение шло с тем же `m_Timer` (время захвата). В затяжном бою задержка
успевала истечь и не работала вовсе, а сразу после захвата, наоборот,
блокировала поиск новой цели. Добавлен отдельный `m_SwitchTimer`, который
стартует в момент потери цели.

### 11.9.6 Компенсация отдачи гасилась сглаживанием

Порядок был: `ApplyRecoilCompensation` → сглаживание. Сглаживание берёт долю от
разницы углов, поэтому и поправку на отдачу оно урезало в те же несколько
процентов: при `Smooth != Off` управление отдачей практически не работало, ствол
уводило вверх. Теперь компенсация применяется **после** сглаживания.

### 11.9.7 Step-сглаживание: шаг в сотых долях градуса

Формула `Step / 100` трактовала настройку как «градусов за тик»: при 100 % это
ровно **1 градус за тик**, то есть доводка на 40 градусов занимала 40 тиков
(больше полусекунды на 66 tick). Ощущалось как «аимбот не наводится». Теперь шаг
— доля оставшейся дистанции (100 % = мгновенно), как и ожидается от процентной
настройки. Дополнительно оба сглаживания нормализуют итоговый угол: yaw мог
выйти за `[-180, 180]`, после чего `ClampAngles` обрезал его в крайнее значение
(разворот через ±180 уезжал «длинной дугой»).

### 11.9.8 Рейдж стрелял, не дождавшись доводки

Остаточный угол перед `IN_ATTACK` проверялся **только** в легит-стиле. Рейдж со
сглаживанием жал огонь с первого тика захвата и высаживал магазин мимо цели
(симптом «рейдж бот стреляет в никуда»). Теперь порог проверяется в обоих
стилях: 2° для легита, 5° для рейджа (хитбокс). В легите, пока ствол не доведён,
снимается и «ручной» огонь.

### 11.9.9 Прочее

* `Target Selection = Damage` без `AutoWall` сравнивал цели по нулевому урону
  (урон считает только трасса прострела) — режим вырождался в «первый живой».
  Добавлен `EstimateDamage()`: урон оружия с затуханием по дистанции и
  коэффициентом брони из данных ствола.
* `OnKeyEvent` при `Mode != 2` выходил, не сбрасывая `m_bKeyPressed`: если
  клавишу отпускали после смены режима или оружия со своим конфигом, флаг
  навсегда оставался `true` и «On Press» работал как «Always On». Также
  добавлена проверка `Key <= 0` (иначе `wParam == 0` не совпадал никогда) и
  `Config::Current` на `nullptr`.
* `m_bChangeTarget` инициализировался как `false` — на старте цель не искалась,
  пока флаг не выставит какая-нибудь другая ветка.
* Ветки простоя (Silent вне выстрела, «On Press» с отпущенной клавишей) теперь
  явно отпускают цель.

### Проверка

`dev-harness/aim_test.cpp` прогоняет **реальный** код доводки: функции
`ApplyStepSmooth`/`ApplyLinearSmooth` вырезаются из `Aimbot.cpp` скриптом
`extract_aim.py` в `aim_smooth.inc`, поэтому тест не может разойтись с
источником. Проверяются сходимость, отсутствие перелёта, разворот через ±180,
крайние значения и разные скорости по осям.

| Сборка | Результат |
| --- | --- |
